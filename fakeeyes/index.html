01 더줌코리아 / 마블워크 / 광고 보상

광고를 봤는데 보상이 없다면,
어느 단계에서 끊겼는지부터

한 달간 앱 이벤트, 광고사의 시청 확인, 서버 지급 기록을 대조했습니다. 같은 ‘보상 누락’ 안에 있던 서로 다른 세 원인을 나눠 고쳤습니다.

2026.08 - 09 집중 추적 · Flutter 광고 처리 / NestJS 검증·복구 / 운영 계측

451건복구 로직 배포 후 30일간
서버가 대신 지급한 보상

앱으로 돌아오지 않아도
확인된 보상을 처리하도록 바꿨습니다.

정상 시청을 거절하던 검증

앱과 서버가 광고 ID를 서로 다른 형식으로 비교하고 있었습니다. ID 정규화 기준을 맞춰 정상 광고를 거절하던 경로를 수정했습니다.

닫기보다 늦게 온 보상 콜백

광고가 닫히자 객체를 먼저 정리해 보상 콜백을 놓쳤습니다. 닫기와 보상 처리를 분리하고 보상 판정 이후에 객체를 정리하도록 수명주기를 바꿨습니다.

앱 종료로 사라진 지급 요청

광고사는 시청을 확인했어도 앱이 종료되면 지급 요청이 오지 않았습니다. 시청 전에 지급 목적과 대상을 기록하고, 서버가 미지급 건을 찾아 처리하게 했습니다.

누락을 고치다 중복 지급을 만들지 않도록

시청 확인 한 건은 한 번만 사용하고, 기존 날짜·한도 검증을 함께 적용했습니다. 451건은 복구 경로의 지급 건수이며 전체 광고의 성공률을 뜻하지 않습니다.

02 더줌코리아 / 마블워크 / 쿠폰 교환

응답이 없다는 이유로 환불하면,
쿠폰과 포인트가 함께 나갑니다

발행사는 쿠폰을 발급했지만 응답만 유실될 수 있습니다. 발행 실패와 결과 미확인을 구분하고, 외부 시스템과 DB 사이에서 거래를 잃지 않도록 설계했습니다.

NestJS · PostgreSQL · 잔액 잠금 / 교환 상태 전이 / 실패 경로 테스트

설계를 바꾼 제약

당시 발행사에는 거래 상태 조회 API가 없었습니다. 자동 환불보다 확인 가능한 보류 상태로 남기는 것을 우선했습니다.

응답에 따라 달라지는 거래 처리
발행 결과거래 상태포인트 처리
정상 발행완료쿠폰 저장 · 차감 유지
명시적 거절실패차감한 포인트 반환
타임아웃·응답 유실결과 미확인자동 환불 보류 · 운영자 확인

동시 교환과 외부 실패를 따로 방어

잔액 확인·차감·대기 거래 기록을 한 트랜잭션으로 묶었습니다. 잠금은 동시 잔액 변경을, 상태 기록은 불확실한 외부 결과를 다루도록 역할을 나눴습니다.

성공 응답보다 실패 분기를 검증

명시적 거절은 환불하고, 외부 호출 예외는 보류하는 경로를 테스트로 구분했습니다. 조회 API가 없는 만큼 운영자의 확인 부담이 남는 선택입니다.

Next.js · TypeScript · NestJS · 운영 화면 / API / 업무 상태 설계

정책 운영

보상 정책·주사위 아이템 확률·이벤트 조건·앱 점검 설정을 편집하게 했습니다. 확률 합계 등 정책 조건을 검증하고 변경 후 서비스의 설정 캐시를 무효화했습니다.

캠페인 운영

대상 확인부터 발송 결과까지

대상 미리보기·기기 테스트·즉시/예약/반복 발송·성공/실패 이력을 연결했습니다. 미리보기와 실제 발송에 같은 수신 조건을 적용했습니다.

고객 대응

지급 내역을 보고 사유를 남겨 조정

포인트·쿠폰·광고·활동 이력을 모아 문의를 확인하게 했습니다. 앱 적립과 관리자 조정이 겹쳐도 잔액을 덮어쓰지 않도록 잔액과 지급 원장을 함께 처리했습니다.

이벤트 운영

안내 성공과 지급 완료를 구분

알림톡 실제 발송이 성공한 경우에만 안내 완료로 바꿨습니다. 실패는 재시도 대상으로 남기고 재발송 확인과 상품 지급 완료 기록을 구분했습니다.

운영 상태의 의미를 끝까지 맞추기

‘버튼을 눌렀다’와 ‘발송이 성공했다’를 분리했습니다. 상품의 실제 지급은 수기이며, CMS에서는 안내와 지급 완료 기록을 관리합니다.

04 더줌코리아 / 마블워크 / AWS 운영

API와 배치를 나누고,
실패를 진단·재시도할 수 있게

사용자 요청, 운영 요청, 정기 작업은 실행 방식과 수명이 다릅니다. 각각 별도 Elastic Beanstalk 환경으로 나누고 배치는 Worker tier와 SQS로 실행하게 했습니다.

AWS EB · SQS · Docker · SSM · CloudFormation · 빌드·배포 / 장애 진단

500 한 줄로 끝나던 결산 실패

작업명·메시지 ID·예약 시각·스택·소요 시간을 남겨 실패를 추적하도록 개선했습니다. 오류를 기록한 뒤 다시 반환해 SQS가 실패한 작업을 성공으로 삭제하지 않게 했습니다.

새 설정을 고쳐도 배포가 막히던 이유

EB가 기존 컨테이너를 내리는 단계에서 잘못된 환경 파일을 먼저 읽었습니다. 뒤의 predeploy까지 도달하지 못하므로, 더 이른 prebuild에서 기존 환경 파일을 복구하도록 순서를 바꿨습니다.

설정값을 안전하게 전달하는 경계

SSM 값을 셸 문법으로 쓰면 Docker Compose가 다르게 해석할 수 있었습니다. 개행·달러 기호·따옴표가 보존되는 Compose 형식으로 직렬화하고, 실행 모드와 설정 저장 경로를 분리했습니다.

재전달과 중복 업무는 별개의 문제

SQS의 재전달을 허용하되, 도메인의 완료 상태와 지급 원장으로 처리 여부를 확인하는 구조를 사용했습니다. 프로세스를 나눠도 DB는 공유하므로, 작업별 트랜잭션과 중복 처리 방어가 함께 필요했습니다.

React · TypeScript · Flutter · JS Bridge · 게임 제작·서버 개발은 팀과 협업

게임 결과 제출·광고 대기·보상 확인을 상태로 구분했습니다. 광고 재시도 때 이미 제출한 게임 결과를 다시 보내지 않도록 완료한 단계와 재시도할 단계를 분리했습니다.

여러 중단 사유를 함께 관리
