01소개

AI에게 요청만 하지 않습니다. 구조와 방향은 제가 정하고, 문제를 제대로 파악해 설계한 뒤에 진행합니다.

무엇을 만들지, 어떤 구조로 나눌지를 먼저 정하고 구현을 맡깁니다. AI가 쓴 코드도 제가 쓴 코드와 같은 테스트와 리뷰를 통과해야 합니다. 코드를 쓰는 속도가 빨라질수록 방향을 정하고 결과를 검증하는 사람의 몫이 커진다고 생각합니다.

  1. 01

    정상 흐름보다 실패하는 경우를 먼저 따집니다.같은 요청이 두 번 오거나, 외부 시스템이 응답하지 않거나, 요청이 위조됐을 때 무엇이 틀어지는지부터 정리하고, 그 경우에도 데이터가 맞도록 구조를 잡습니다. 돈이 오가는 코드에서는 빠른 것보다 틀리지 않는 것을 먼저 챙깁니다.

  2. 02

    원인까지 고치고, 다시 생기지 않게 막아 둡니다.증상만 막고 넘어가지 않고 원인을 끝까지 따라갑니다. 고친 뒤에는 같은 문제가 다시 생기지 않도록 테스트나 배포 검증에 검사를 넣고, 무엇이 왜 일어났는지 기록해 팀과 공유합니다.

  3. 03

    AI에게 맡길 일과 사람이 결정할 일을 나눕니다.에이전트에게 권한을 넓게 주더라도, 되돌리기 어려운 작업과 배포는 사람이 승인해야 진행되도록 코드로 강제합니다. 에이전트가 한 일은 기록으로 남겨 나중에 따라갈 수 있게 하고, 실패했을 때 어디서 멈추는지를 먼저 설계합니다.

  4. 04

    만든 서비스는 운영까지 맡습니다.기획 단계부터 설계, 출시, 운영까지 한 서비스를 끝까지 맡아 왔습니다. 배포에서 끝내지 않고, 실제 사용자에게 어떻게 동작하는지 지표와 로그로 확인하는 데까지를 제 일로 봅니다.

    장애 대응 · 마블워크 · 2026.09

    광고를 끝까지 봤는데 보상이 들어오지 않던 유실

    광고 서버의 시청 검증은 도착했는데 앱의 지급 요청이 나가지 않은 건이 있었습니다. 원인은 두 가지였고, 앱이 끝까지 살아 돌아와야만 보상이 나가는 구조가 공통 뿌리였습니다.

    광고가 닫히자마자 폐기늦게 온 보상 이벤트 유실

    광고 도중 앱 종료지급 요청이 나가지 않음

    판정 뒤 폐기 · 보상 의도 기록5분 주기 복구가 대신 지급

    1. 증상

      광고를 끝까지 봤는데 보상이 들어오지 않았습니다. 광고 서버의 시청 검증(SSV)은 도착했는데 앱의 지급 요청은 한 번도 나가지 않은 상태였습니다.

    2. 증거

      상용에서 16시간 동안 시청 100건 중 10건이 이 상태였습니다. 하루 동안 유실된 15건 중 13건은 광고를 보는 도중 앱 프로세스가 종료된 경우였습니다.

    3. 원인

      광고가 닫히자마자 광고 객체를 폐기해서, 닫힌 뒤 1.5초 안에 늦게 오는 보상 이벤트를 SDK가 버리고 있었습니다. 또 지급이 앱 복귀에만 달려 있어서, 서버는 시청 사실을 알아도 무엇을 줄지 몰랐습니다.

    4. 조치

      광고 폐기를 보상 판정이 끝난 뒤로 옮겼습니다. 광고를 띄우기 직전에 무엇을 위한 광고인지 서버에 남기고, 5분마다 쓰이지 않은 시청 검증을 찾아 앱이 못 한 지급 호출을 그대로 재생합니다.

    5. 재발 방지

      지급 로직을 새로 만들지 않고 같은 호출을 재생해서 일일 한도와 날짜 경계가 그대로 적용되고, 이중 지급은 시청 검증을 원자적으로 한 번만 소비하는 기존 구조가 막습니다. 광고 단계별 결과도 DB에 남겨 다음 유실은 바로 추적합니다.

    10 / 10016시간 동안 검증은 왔는데 지급 요청이 없던 시청

    13 / 15하루 유실 중 광고 도중 앱이 종료된 경우

    64→100%

    장애 대응 · 미네르바 · 2026.09

    모든 사용자가 한도 하나를 나눠 쓰던 rate limit 장애

    사용자가 늘자 제휴 매체 앱의 혜택 탭이 열리지 않았습니다. 처음부터 있던 구조가 트래픽이 늘면서 드러난 장애였습니다.

    수정 전 · 전체 공용 120/분

    200429 RATE_LIMITED

    수정 후 · 사용자별 버킷

    200

    1. 증상

      혜택 탭을 열면 “콘텐츠를 불러오지 못했어요(RATE_LIMITED)”가 떴습니다. 막힌 곳은 혜택 API가 아니라 화면을 여는 요청이었습니다.

    2. 증거

      외부에서 보낸 요청의 남은 한도가 119가 아니라 50으로 왔습니다. 모든 사용자가 분당 120회짜리 버킷 하나를 나눠 쓰고 있다는 직접 증거였습니다.

    3. 원인

      프록시 뒤에서 실제 IP를 복원하지 않아 모든 요청이 같은 주소로 보였습니다. 헬스체크도 분당 8회씩 한도를 깎았고, 화면 하나를 열 때 요청이 19~25개 나가서 다섯 명만 동시에 들어와도 한도가 찼습니다.

    4. 조치

      서명을 검증한 토큰으로 사용자를 식별해 버킷을 나누고, 실제 IP는 홉 수가 아닌 신뢰 대역으로 복원해 헤더 위조가 통하지 않게 했습니다. 헬스체크는 한도에서 빼고, 한도 값은 환경변수로 조절하게 했습니다.

    5. 재발 방지

      테스트로 버킷 분리, 위조 헤더 무효, 가드 실행 순서를 고정했습니다. 한도 초과가 헬스체크 실패로 잡혀 서버가 내려갈 수 있던 경로도 함께 막았고, 로그로 확인하지 못한 부분은 확인 방법과 함께 장애 보고서에 남겼습니다.

    증권사 API는 부를 때마다 응답이 느렸고, 여러 사용자가 동시에 부르면 호출 제한에 걸릴 수 있었습니다. 6천 개가 넘는 종목을 LIKE 쿼리로 찾으니 검색도 느렸습니다.
    해결
    마지막 갱신 시각을 보고 오래된 데이터만 외부 API로 갱신하고, 사용자 요청은 항상 DB에서 읽게 했습니다. 종목 검색은 Elasticsearch로 분리해 한글 형태소 분석기로 자동완성을 만들었습니다. 로그인은 5회 실패하면 5분 잠그고, 서버가 재시작돼도 유지됩니다.
    결과
    조회가 외부 API 호출에 기대지 않게 됐고, 종목이 많아도 자동완성이 됩니다.

    피부암 진단 앱 자체 이미지 인식 모델

    문제
    피부암은 점과 헷갈려 조기에 발견하기 어렵고, 흑색종은 다른 부위로 빠르게 전이됩니다.
    해결
    공개 피부 병변 이미지(ISIC 2019) 약 6,400장을 피부암 6종과 피부암이 아닌 질환 1종, 모두 7개로 나눠 분류 모델을 직접 학습시켰습니다. 같은 데이터로 CNN, 오토인코더, PCA, MLP를 비교했고, GAN으로 피부 이미지를 생성하는 실험도 했습니다. 앱에서 피부를 찍으면 의심되는 병명과 그 정도를 보여주고, 정확한 진단은 병원에서 받도록 안내합니다.
    결과
    7개 분류에서 CNN이 정확도 75%로 가장 높았고, 상명대학교 전공소모임 대상을 받았습니다.
