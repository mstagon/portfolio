01소개

AI에게 요청만 하지 않습니다. 구조와 방향은 제가 정하고, 문제를 제대로 파악해 설계한 뒤에 진행합니다.

무엇을 만들지, 어떤 구조로 나눌지를 먼저 정하고 구현을 맡깁니다. AI가 쓴 코드도 제가 쓴 코드와 같은 테스트와 리뷰를 통과해야 합니다. 코드를 쓰는 속도가 빨라질수록 방향을 정하고 결과를 검증하는 사람의 몫이 커진다고 생각합니다.

  1. 01

    정상 흐름보다 실패하는 경우를 먼저 따집니다.같은 요청이 두 번 오거나, 외부 시스템이 응답하지 않거나, 요청이 위조됐을 때 무엇이 틀어지는지부터 정리하고, 그 경우에도 데이터가 맞도록 구조를 잡습니다. 돈이 오가는 코드에서는 빠른 것보다 틀리지 않는 것을 먼저 챙깁니다.

  2. 02

    원인까지 고치고, 다시 생기지 않게 막아 둡니다.증상만 막고 넘어가지 않고 원인을 끝까지 따라갑니다. 고친 뒤에는 같은 문제가 다시 생기지 않도록 테스트나 배포 검증에 검사를 넣고, 무엇이 왜 일어났는지 기록해 팀과 공유합니다.

  3. 03

    AI에게 맡길 일과 사람이 결정할 일을 나눕니다.에이전트에게 권한을 넓게 주더라도, 되돌리기 어려운 작업과 배포는 사람이 승인해야 진행되도록 코드로 강제합니다. 에이전트가 한 일은 기록으로 남겨 나중에 따라갈 수 있게 하고, 실패했을 때 어디서 멈추는지를 먼저 설계합니다.

  4. 04

    만든 서비스는 운영까지 맡습니다.기획 단계부터 설계, 출시, 운영까지 한 서비스를 끝까지 맡아 왔습니다. 배포에서 끝내지 않고, 실제 사용자에게 어떻게 동작하는지 지표와 로그로 확인하는 데까지를 제 일로 봅니다.

    1. 증상

      혜택 탭을 열면 “콘텐츠를 불러오지 못했어요(RATE_LIMITED)”가 떴습니다. 막힌 곳은 혜택 API가 아니라 화면을 여는 요청이었습니다.

    2. 증거

      외부에서 보낸 요청의 남은 한도가 119가 아니라 50으로 왔습니다. 모든 사용자가 분당 120회짜리 버킷 하나를 나눠 쓰고 있다는 직접 증거였습니다.

    3. 원인

      프록시 뒤에서 실제 IP를 복원하지 않아 모든 요청이 같은 주소로 보였습니다. 헬스체크도 분당 8회씩 한도를 깎았고, 화면 하나를 열 때 요청이 19~25개 나가서 다섯 명만 동시에 들어와도 한도가 찼습니다.

    4. 조치

      서명을 검증한 토큰으로 사용자를 식별해 버킷을 나누고, 실제 IP는 홉 수가 아닌 신뢰 대역으로 복원해 헤더 위조가 통하지 않게 했습니다. 헬스체크는 한도에서 빼고, 한도 값은 환경변수로 조절하게 했습니다.

    5. 재발 방지

      테스트로 버킷 분리, 위조 헤더 무효, 가드 실행 순서를 고정했습니다. 한도 초과가 헬스체크 실패로 잡혀 서버가 내려갈 수 있던 경로도 함께 막았고, 로그로 확인하지 못한 부분은 확인 방법과 함께 장애 보고서에 남겼습니다.
