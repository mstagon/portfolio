02보상 기록

보상 기록과 쿠폰 교환 보류

어느 경로로 들어오든 같은 검증 체인을 거쳐 기록에 쌓이게 했습니다. 외부 발행 결과를 모를 때는 환불하지 않고 보류합니다.

1문제

같은 거래가 두 번 들어오거나 외부 응답이 끊겨도 잔액과 기록이 어긋나지 않아야 했습니다.

보상은 광고 시청 검증, 오퍼월 콜백, 미네르바 포스트백으로 들어오고 기프티콘 교환으로 나갑니다.

2위험3설계

  • 위험. 같은 거래가 다시 오면 보상도 다시 나갑니다.SQS와 외부 콜백은 같은 메시지를 다시 보낼 수 있고, 동시에 들어온 요청은 조회만으로 막을 수 없습니다.

    설계. 서명 → 거래 ID 멱등 → 행 잠금 → 한도 → 기록광고 검증은 ECDSA, 포스트백은 HMAC으로 서명을 확인하고, 거래 ID UNIQUE와 pessimistic_write 잠금, 일 · 월 한도를 지난 뒤에만 append-only 기록에 씁니다.

  • 위험. 잔액만 고치면 왜 그 값이 됐는지 남지 않습니다.주사위 잔액을 걸음 기록에서 다시 계산하던 때, 다 쓴 광고 주사위가 동기화마다 다시 생겼는데 흔적이 없었습니다.

    설계. 잔액 변동과 적립 기록을 한 트랜잭션에적립 기록 함수는 트랜잭션을 받아 잔액 변동과 같은 트랜잭션에서 쓰게 했고, 주사위 기록에는 변동 뒤 잔액을 남깁니다. 포인트 음수는 DB의 CHECK 제약이 막습니다.

  • 위험. 발행 응답이 끊겼을 때 환불하면 쿠폰과 포인트가 함께 나갑니다.발행 호출이 트랜잭션 안에 있어 응답만 유실돼도 포인트를 돌려줬고, 재시도는 새 거래 ID로 나갔습니다. 발행사에는 거래 조회 API가 없었고, 출시 전 교차 검수에서 P0로 확정됐습니다.

    설계. 2단계 커밋과 UNKNOWN 보류포인트 차감과 PENDING을 먼저 커밋하고, 트랜잭션 밖에서 고정 거래 ID로 발행합니다. 분명한 거절만 환불하고, 결과를 모르면 UNKNOWN으로 두어 운영자가 확인해 정산합니다.

  • 위험. 운영자 취소도 이중 환불 경로였습니다.어드민 쿠폰 취소는 REFUNDED만 막아 이미 환불한 FAILED 건을 또 환불할 수 있었고, 잠금 없이 다시 읽어 동시 취소 2건이 모두 통과할 수도 있었습니다.

    설계. 허용 상태 목록과 잠금 후 재조회취소 대상을 COMPLETED와 UNKNOWN 두 상태로 좁히고, 행을 잠가 다시 읽은 뒤 잔액을 더하는 UPDATE 한 번으로 환불합니다.

03알림 · CRM

알림 발송 계층

세 경로에서 생긴 알림을 세 채널로 보냅니다. 중복은 DB에서 먼저 차지하는 방식으로, 법적 동의와 사용자 설정은 서로 다른 게이트로 막았습니다.

1문제

큐 재전달이나 서버 여러 대 때문에 같은 알림이 두 번 나가면 안 되고, 광고성 알림은 정보통신망법 §50의 동의와 야간 제한을 지켜야 했습니다.

알림은 친구 · 추첨 · 랭킹 같은 사건, 정해진 시각의 크론, 운영자 발송에서 생깁니다.

2위험3설계

  • 위험. 푸시가 막힌 사용자는 당첨 소식도 받지 못했습니다.당첨 통지를 FCM으로만 보내, 기기 토큰이 없는 사용자는 당첨을 보지 못했습니다.

    설계. 알림함 · FCM · 알림톡을 독립된 3계층으로알림함은 수신 설정과 상관없이 항상 1명 1행으로 쌓고, 게이트는 푸시에만 겁니다. 한 채널이 막혀도 다른 채널은 나갑니다.

  • 위험. 큐 재전달과 다중 인스턴스에서 같은 알림이 두 번 나갑니다.SQS는 at-least-once로 다시 전달하고 서버가 여러 대라, 같은 사용자에게 푸시 2회와 알림함 2행이 생길 수 있었습니다.

광고 보상 유실 복구와 콜백 검증

광고 서버의 시청 검증은 도착했는데 앱이 죽어 보상이 나가지 않던 유실을 서버가 복구하게 했습니다. 오퍼월 콜백 위조와, 수정 뒤 테스트 서버에서 정상 콜백이 막힌 문제도 고쳤습니다.

1문제

24시간 유실 15건 중 13건은 광고를 보는 도중 앱 프로세스가 종료된 경우였고, 서버는 시청 사실을 알고도 무엇을 줄지 몰랐습니다.

보상형 광고는 광고 서버가 시청을 검증(SSV)한 뒤 앱이 지급을 요청해야 보상이 나갔습니다.

2위험3설계

  • 위험. 지급이 앱 복귀에만 달려 있었습니다.검증 기록에는 그 광고가 어느 지면의 무엇을 위한 것인지가 없어, 앱이 죽으면 서버가 줄 것을 정할 수 없었습니다.

    설계. 광고 직전 보상 의도 기록과 5분마다 도는 복구 작업광고 직전 지면과 대상을 의도로 남기고, 5분마다 소비되지 않은 검증과 조인해 대신 지급합니다. 24시간 안의 건을 한 번에 200건까지 집습니다.

  • 위험. 복구용 지급 경로를 따로 두면 두 경로가 갈라집니다.갈라진 경로는 일일 한도 우회 같은 사고로 이어집니다.

    설계. 같은 도메인 호출을 재생, 검증은 한 번만 소비앱이 못 한 호출을 그대로 재생해 한도와 KST 날짜 경계가 그대로 적용됩니다. 검증 행은 consumed_at IS NULL 조건부 UPDATE 한 번으로 소비 처리해, 늦게 온 앱 요청과 복구 작업 중 한쪽만 성공합니다.

  • 위험. 허용 목록 가드가 위조할 수 있는 헤더를 믿었습니다.오퍼월 적립 콜백 가드가 X-Forwarded-For 맨 앞 값을 믿어 헤더만으로 우회할 수 있었습니다(상용 검수 blocker).

    설계. 요청 주소와 허용 목록 양쪽을 정규화양쪽에서 ::ffff: 접두를 벗겨 비교하고, 정규화가 허용 범위를 넓히지 않는지까지 테스트로 고정했습니다.
