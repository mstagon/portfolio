01 / OVERVIEW

어떤 프로젝트인가요?

걸음으로 주사위를 얻고, 보드를 이동하며 모은 포인트를 상품 교환과 이벤트 응모에 사용하는 서비스입니다. Flutter 앱, NestJS API, Next.js CMS와 운영 인프라를 개발하고 2026년 8월 Google Play·App Store·원스토어에 출시했습니다.

  1. 01걷기 · 보드 · 광고
  2. 02보상 검증 · 지급 원장
  3. 03교환 · 응모 · 운영

02 / ENGINEERING

구현과 판단

01

한 달 동안 광고 보상의 전체 경로를 추적

광고는 끝났는데 보상이 없는 문제를 앱 이벤트, 광고사의 시청 확인, 서버 지급 기록까지 연결해 조사했습니다. 광고 ID 형식 차이, 늦게 도착한 보상 콜백, 앱 종료로 사라진 지급 요청을 구분하고 각각 수정했습니다. 광고 객체는 보상 판정이 끝난 뒤 정리하도록 바꿨습니다.

02

앱이 닫혀도 확인된 보상은 지급

시청 전에 지급 목적과 대상을 기록하고, 광고사가 시청을 확인했지만 아직 지급하지 않은 건을 5분마다 찾아 기존 지급 로직으로 처리했습니다. 날짜·한도 검증과 중복 소비 방지를 함께 적용했습니다. 배포 후 30일간 서버 대리지급 451건을 집계했습니다.

03

쿠폰 응답이 없다는 이유로 환불하지 않기

외부 발행사가 응답하지 않아도 쿠폰은 이미 발급됐을 수 있습니다. 확정 실패와 결과 미확인을 나누고, 미확인 주문을 무조건 재발급·환불하지 않도록 처리했습니다. 외부 호출을 DB 트랜잭션 밖으로 분리해 긴 잠금도 피했습니다.

04

운영자가 업무를 끝낼 수 있는 CMS

대상 미리보기·테스트 발송·즉시/예약/반복 푸시·성공/실패 이력을 연결했습니다. 고객의 보상·쿠폰·활동 이력을 한곳에서 확인하고 사유를 남겨 포인트를 조정하게 했습니다. 앱 적립과 관리자 조정이 겹쳐도 잔액을 덮어쓰지 않도록 잠금과 지급 원장을 함께 처리했습니다.

05

외부 발송 결과와 운영 상태를 일치

당첨자 알림톡이 실제로 성공한 경우에만 안내 완료로 기록하고, 실패한 건은 재시도 대상으로 남겼습니다. 재발송과 상품 지급 완료 기록을 구분해 운영자가 현재 처리 단계를 알 수 있게 했습니다.

06

API 트래픽과 정기 작업의 실행 경계

메인 API, CMS API, 정기 작업을 별도 Elastic Beanstalk 환경으로 나눴습니다. 워커에는 SQS 기반 실행을 적용하고 실패를 재시도 가능한 상태로 남겼습니다. 배포 훅의 실행 순서와 환경 설정 복원도 실제 배포 흐름에 맞춰 다뤘습니다.

07

제품 변경을 측정할 수 있는 구조

회원가입 전 보드 체험, 광고 진입 위치, 가입 보상과 교환 기준을 실험할 수 있도록 지표와 설정을 연결했습니다. 변경 전후의 단순 비교와 무작위 A/B 실험을 구분해 해석했습니다.

결과와 범위
